# MIAGuard 阶段性汇报讲稿与 PPT 提纲

> 用途：向老师介绍近期已完成的攻击复现、防御实验框架、攻击模式/经验沉淀，以及 AG News 上的阶段性实验结果。  
> 建议时长：8～12 分钟；建议页数：6 页正文 + 1 页备用页。  
> 汇报原则：重点展示“已经做成的闭环”和“由实验得到的真实结论”，不把当前 Rule-only 原型表述为最终成熟方案。

---

## 0. 一句话主线

本阶段已经把多种 RAG 成员推理攻击接入同一套可复现实验流程，并搭建了能对查询进行识别、干预和评估的两阶段防御框架；在 AG News 的 32+32 平衡实验中，防御能降低整体攻击效果，但正常查询误报仍然偏高，是下一阶段的重点优化对象。

可以用下面这条链路串起整份 PPT：

```text
攻击复现
  → 攻击知识与离线查询沉淀
  → 统一防御入口
  → 防御前后同条件回放
  → 安全性、可用性与开销评估
  → 发现问题并进入下一轮优化
```

## 2. 第 2 页：四种攻击算法复现

### 页面标题

**已复现的成员推理攻击及其作用**

### 页面内容

| 攻击 | 核心思路 | 在系统中的成员性信号 |
|---|---|---|
| Direct RAG-MIA | 直接询问给定文本是否出现在 RAG 上下文中 | 模型的 Yes / No 回答 |
| S²-MIA | 给出原文前缀，要求根据上下文补全 | 生成文本与原文的语义相似度 |
| Masked MIA | 遮盖原文词语，要求恢复被遮盖内容 | 被正确恢复的关键词比例 |
| IA | 用多轮间接事实问题逐步探测文档信息 | 多轮回答得分的聚合结果 |

可以在表格右侧或下方再补一句：

> 四类攻击覆盖了直接确认、文本复现、内容恢复和间接事实探测四种不同的攻击方式。

### 讲解参考

“四种攻击并不是简单换问法。Direct 最直接地确认文档是否出现，S²-MIA 和 Masked MIA 关注模型对原文内容的复现能力，IA 则通过看似普通的事实问题累积证据。把它们放在一起，能避免防御只对单一攻击模板有效。”

### 可放的验证信息

- 四种攻击已进入统一实验入口；
- 每种攻击都有对应的成员性评分方式；
- 本轮主实验中，每种攻击使用同一批 64 个文档（32 member + 32 non-member）。

### 可能被问到的问题

**问：为什么要复现四种，而不是只选一种？**  
答：不同攻击利用的信号不同。只对一种攻击有效的防御，可能只是屏蔽了固定措辞；多攻击对比更能检验防御是否真正降低了泄露信号。

## 3. 第 3 页：数据与 Query Bank（简要带过）

### 页面标题

**冻结 Query Bank：让攻击和防御比较可复现、可公平**

### 页面内容

这一页不需要重讲数据集构建细节，只保留以下关键信息：

| 项目 | 当前 AG News Query Bank |
|---|---:|
| 文档数 | 100（50 member + 50 non-member） |
| 查询总数 | 5,000 |
| 每文档查询数 | 50 |
| 查询类型 | Benign、Direct、S²、Masked、IA |
| 校验状态 | `valid` |

建议配一条简图：

```text
源文档 + 成员标签
  → 离线生成并校验多类查询
  → Query Bank（版本、哈希、查询 ID）
  → 实验按固定 seed 抽取
  → 防御前后复用完全相同的查询
```

### 讲解参考

“Query Bank 可以理解为提前构建好的标准题库。攻击查询不在正式实验中临时生成，而是先离线生成、校验、编号和冻结。这样无防御和有防御的对比使用完全相同的文档与问题，结果差异就能更明确地归因于防御机制。”

### 本轮实验为什么是 32+32

“Query Bank 原始覆盖 50+50 文档，但当前 IA 需要每个文档具备三轮且 yes/no 均衡的有效问题。过滤后有 33 个 member 和 32 个 non-member 满足条件，因此主实验取最大平衡规模 32+32。这个选择是为了让各类攻击的 Accuracy、F1 和混淆矩阵比较公平。”

## 4. 第 4 页：防御实验框架和整体流程

### 页面标题

**防御实验框架：识别风险，再控制 RAG 可访问的信息**

### 页面内容

建议直接画成下面的流程图：

```text
冻结查询（攻击 / Benign）
          ↓
      RAG 检索
          ↓
查询级风险判断 ──────→ 会话级风险判断
          ↓                    ↓
          └──── 总风险与风险等级 ────┘
                            ↓
                  访问控制动作选择
             ┌────────┼─────────┐
           allow  restrict_context  deny_sensitive_answer
             ↓          ↓                 ↓
        完整上下文   截短上下文       不提供检索上下文
             └──────────┴───────────────┘
                            ↓
                    RAG 回答与日志记录
                            ↓
          防御前后攻击指标 + Benign 误报率 + 延迟
```

### 各模块应该怎么介绍

**1. 统一事件层**  
将不同攻击和正常查询统一成相同格式的事件，包含 query、session、检索文档、攻击类型、成员标签等。这里要强调：攻击类型和成员标签只用于最后评估，不作为检测器输入，避免“拿答案做判断”。

**2. 查询级风险判断**  
当前原型根据查询中明显的成员确认、内容恢复、原文续写和 IA 模板等信号，输出查询风险和命中原因。

**3. 会话级风险判断**  
记录同一个 session 最近几轮检索到的文档。当多轮查询持续集中于同一目标文档时，提高会话风险。该机制为多轮攻击预留了入口。

**4. 访问控制层**  
根据 low / medium / high 三档风险选择动作：低风险正常回答；中风险限制可见上下文；高风险不提供原始检索上下文并返回安全响应。

**5. 统一评估层**  
记录风险、触发原因、访问动作、检索结果、回答和攻击得分，最终同时计算安全性、正常可用性和额外开销。

### 讲解参考

“防御不是简单拒绝所有可疑问题，而是在每个查询经过 RAG 前后做风险判断，并根据风险程度改变模型能看到的检索上下文。这样既可以看攻击是否被削弱，也可以通过 Benign 查询检查正常请求有没有被错误拦截。”

### 需要诚实说明的边界

当前版本是 **Rule-only 原型和系统 baseline**：它已经完成闭环，但规则对已知英文攻击模板有依赖，不能把当前检测效果直接等同于泛化能力。后续会用语义特征、LLM Judge 和更真实的多轮会话进一步增强。

## 5. 第 5 页：攻击模式/经验库如何构建

### 页面标题

**攻击模式库：把“攻击经验”沉淀为可更新、可复现实验知识**

### 先明确概念

本项目中可以把“攻击经验库”拆成两层来讲：

| 层次 | 当前实现 | 它解决的问题 |
|---|---|---|
| 攻击模式库（Attack Pattern Library） | 每类攻击的定义、特征、排除条件、判断示例和版本 | 如何识别某类攻击意图 |
| Query Bank | 基于具体数据集生成的攻击/正常查询、标签、哈希和版本 | 用什么固定样本做公平实验 |

这样表述比把两者都称作“经验库”更准确：**模式库沉淀攻击知识，Query Bank 冻结实验数据。**

### 攻击模式库的构建流程

```text
复现一种攻击
   ↓
提炼攻击目标、关键语言特征、必要上下文和排除条件
   ↓
写入该攻击的 Pattern 文档
   ↓
在 manifest 中登记名称、版本和入口
   ↓
加入判断示例，并通过校验与回归测试
   ↓
正式实验保存模式库快照
   ↓
后续可根据失败案例继续更新模式与版本
```

### 当前已经沉淀的内容

- 已登记 Direct RAG-MIA、S²-MIA、Masked MIA、IA 四类模式；
- 每种模式描述攻击目标、判断信号和不应误判为攻击的情况；
- 模式库有 manifest 和版本信息；
- 正式实验会保存本次使用的模式库快照，避免之后更新规则导致历史结果无法复现。

### 讲解参考

“攻击经验库不是简单存一批攻击样本，而是把每种攻击的目的、特征、上下文要求、典型示例和版本一起保留下来。这样新增攻击时有统一的登记方式；更新规则时也能追溯某次实验到底使用了哪一版攻击定义。”

### 后续可扩展方向（点到为止）

后续可以在模式库中补充：绕过方式、易混淆的正常查询、不同语言表达、历史检测表现和适用的防御动作。这样它会从“攻击定义库”逐步成长为更完整的攻击经验库。

## 6. 第 6 页：实验结果与结论

### 页面标题

**AG News 32+32 结果：防御有效，但正常可用性仍需优化**

### 页面核心数字

建议只放下面这张最关键的表，其他细表放备用页：

| 指标 | 无防御 | 有防御 | 结论 |
|---|---:|---:|---|
| 宏平均攻击 Accuracy | 83.20% | 70.31% | 下降 12.89 个百分点 |
| 宏平均攻击 ROC-AUC | 90.12% | 79.11% | 下降 11.01 个百分点 |
| Query Stage 攻击 Recall | — | 100.00% | 攻击查询均被识别 |
| Benign FPR | — | 85.94% | 正常请求误报偏高 |
| 总运行时间 | \- | 约 5 小时 26 分 | 当前 32+32 规模稳定运行 |

再用一行给出各攻击的 Accuracy 变化：

```text
Direct：98.44% → 84.38%   |   S²：85.94% → 78.13%
Masked：75.00% → 60.94%   |   IA：73.44% → 57.81%
```

### 讲解参考

“在同一批文档、同一批查询、同一模型和同一阈值下，只启用防御网关，宏平均攻击准确率下降了 12.89 个百分点，说明防御确实削弱了整体成员推断能力。其中 IA 和 Masked 的下降比较明显；但 S² 的 ROC-AUC 基本不变，说明它仍然保留了较强的排序信号，是需要重点关注的薄弱点。”

### 必须说明的可用性问题

“Query Stage 对攻击查询的召回率达到 100%，但 64 条 Benign 正常查询中有 55 条触发了防御，Benign FPR 达到 85.94%。因此当前结论不能是‘防御已经完善’，而是‘防御闭环已验证有效，但策略偏保守，正常可用性是下一步最需要优化的问题’。”

### 实验公平性一句话

“无防御和有防御复用相同的 64 个文档、冻结查询、向量库、模型和阈值，仅切换 gateway 状态，因此结果差异可以主要归因于防御机制。”

## 7. 第 7 页：总结与下一步

### 页面标题

**阶段总结与下一步计划**

### 已完成

- 复现并统一接入四类 RAG 成员推理攻击；
- 构建 Query Bank，提供冻结、校验和可追溯的实验查询；
- 搭建查询级 + 会话级 + 访问控制的防御实验框架；
- 在 AG News 上完成 32+32 的防御前后公平对比；
- 得到明确的安全性与可用性权衡结论。

### 下一步（按优先级）

1. **降低 Benign 误报**：清洗不自然的正常查询，校准阈值，优化风险证据规则。
2. **增强对 S²-MIA 的防护**：分析为什么其 ROC-AUC 基本不变，并比较更合适的访问控制动作。
3. **补足真实多轮会话评估**：让 Session Stage 在更多多轮攻击与多轮正常对话中得到充分测试。
4. **提高结果稳健性**：在多个随机种子下重复实验，报告均值、标准差或置信区间。
5. **扩展数据集和攻击变体**：验证框架跨数据集、跨表达方式时的适用性。

### 收束讲稿

“目前的阶段成果是搭建了完整、可复现的防御评估闭环，并初步证明防御能够降低成员推断攻击效果。下一阶段不会只追求更高的攻击拦截率，而是重点解决正常查询误报高的问题，在安全性、可用性和开销之间做更可靠的平衡。”

### 备用页 B：为什么不能只看攻击 Accuracy

- 攻击 Accuracy / ROC-AUC：衡量攻击者判断成员身份的能力，**有防御时通常越低越好**；
- 检测器 Precision / Recall / F1：衡量防御器识别攻击意图的能力，**越高越好**；
- Benign FPR：衡量正常请求被错误触发防御的比例，**越低越好**；
- 延迟和显存：衡量工程成本，**越低越好，但需结合稳定性解释**。

### 备用页 C：当前局限

- 当前结果主要来自一个冻结查询种子，尚未形成多随机种子的统计结论；
- Rule-only 检测器对已知攻击模板有依赖，不能代表对改写攻击或跨语言攻击的泛化能力；
- 大多数当前攻击是单轮，Session Stage 的效果尚未被充分激活；
- Benign 查询中仍存在少量自动生成且表达不自然的样本，可能影响误报指标；
- 运行时观察到整卡显存接近 24 GB 且无 OOM，但尚未记录可靠的单进程峰值显存。
